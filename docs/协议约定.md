# 客户端 / 服务端通讯约定

本文记录 335XS 定制层的三条通讯通道、编号规划与新增功能的落地规则。协议常量在两端各有一份 `NativeUIProtocol.h`，一致性由 `Tools/Tests/Test-NativeProtocolSync.ps1` 与 `Test-AddonCommandSync.ps1` 自动校验（已并入 `Run-MigrationTests.ps1`）。

## 一、三条通道

| 通道 | 载体 | 典型用途 | 策略 |
|---|---|---|---|
| NativeUI opcode | `0x521`–`0x525` | 单位资源快照、精确飘字、物品 Tooltip | 新功能首选 |
| addon 消息 | 客户端 `前缀\t命令:参数` → 服务端 `SendPacketToClient(名字, 载荷)` | 特色窗口（98 条请求 / 99 个处理） | 只维护，不扩展 |
| Tooltip 载荷 | `0x524` 查询、`0x525` 返回的字符串 | 物品模板级 / 实例级聚合数据 | 承接原 `UITQ` whisper |

定位：

- opcode：客户端 `WoW/Source/Net/Types.h` + `WoW/Source/Client.cpp`；服务端 `src/server/game/Server/Protocol/Opcodes.h/.cpp` + `Handlers/`
- addon 消息：客户端 `Interface/NativeUI/BundledAddOns/`；服务端 `scripts/Custom/AddonActive/DoAddon.cpp` 及各管理器
- 快照字段：服务端 `Handlers/ChatHandler.cpp` 的 `PattrSendStats/Target/Pet` 与 `NativeResourceFields`；客户端 `Interface/NativeUI/NativeUI.lua` 的 `value(unit, key)`

## 二、opcode 规划

| 编号 | 名称 | 方向 | 说明 |
|---|---|---|---|
| `0x51F` | `TC9_CMSG_PREPARE_FOR_REDIRECT` | C→S | 侧边车，仅服务端定义 |
| `0x520` | `TC9_SMSG_READY_FOR_REDIRECT` | S→C | 侧边车，仅服务端定义 |
| `0x521` | `CMSG_NATIVE_UI_HELLO` | C→S | `uint16 version`（1 旧版 / 2 宽版） |
| `0x522` | `SMSG_NATIVE_UI_SNAPSHOT` | S→C | `uint16 ver, uint8 kind, uint64 guid, uint16 count` + 字段 |
| `0x523` | `SMSG_NATIVE_UI_COMBAT_TEXT` | S→C | 精确伤害/治疗飘字 |
| `0x524` | `CMSG_NATIVE_UI_TOOLTIP_QUERY` | C→S | `uint16 ver, uint32 itemId, uint32 guidLow` |
| `0x525` | `SMSG_NATIVE_UI_TOOLTIP_DATA` | S→C | `uint16 ver, uint32 itemId, uint32 guidLow, uint16 len, payload` |
| `0x526` | `NUM_MSG_TYPES` | — | 两端上界，新增 opcode 必须同步抬高 |

规则：

1. 新增 opcode 从 `0x526` 起顺延，客户端 `Types.h` 与服务端 `Opcodes.h` 必须同名同值。
2. 服务端必须在 `Opcodes.cpp` 注册：CMSG 用 `DEFINE_HANDLER`，SMSG 用 `DEFINE_SERVER_OPCODE_HANDLER`。
   **漏注册不是“少个功能”而是崩溃路径**：`WorldSession::Update` 取 `opcodeTable[opcode]` 后不判空就直接读 `opHandle->Name`，客户端伪造该 opcode 即触发空指针。`0x523` 曾遗漏，已修复。
3. `NUM_MSG_TYPES` 是对外上界，客户端枚举末尾同样如此；加 opcode 忘改上界会被同步脚本抓到。

## 三、快照 kind

| kind | 含义 | 约束 |
|---|---|---|
| 0 | 玩家属性 | `guid` 必须是接收者自身 |
| 1 | 目标 | 取消选择时发 `count = 0` 清空 |
| 2 | 宠物 | — |
| 3 | 可见单位资源 | `guid != 0`；`count = 0` 表示离开视野；只推给能看到该单位的会话 |
| 4 | `IGRO_DATA` | 物品成长扩展载荷 |
| 5 | `UITQ_DATA` | 物品 Tooltip 扩展载荷 |

新增 kind 必须同时抬高 `NativeUIProtocol::LastSnapshotKind` 并在客户端 `Packet_SMSG_NATIVE_UI_SNAPSHOT` 增加分支，否则客户端按非法包丢弃整条消息。

## 四、字段与上限

- 上限：`MaxFields 128`、`MaxKeyBytes 63`、`MaxValueBytes 1023`、`MaxIntegerBytes 79`、`MaxTooltipPayloadBytes 65520`。
- 类型：`0` int64、`1` 字符串、`2` 十进制 int256（仅 v2 握手后可用）。
- 键名 UPPER_SNAKE；服务端用 `PattrAddField(fields, "NAME", ...)` 生成 `NAME=VALUE`，`ATTR_<ItemMod>` 与 `RATING_<n>` 为带后缀的族。
- 大数必须走 type 2 十进制字符串；浮点只允许用于血条几何比例，不能承载 256 位数据。
- 线协议字段宽度保持 12340 原样；客户端升级到 x64 不改变任何一个线上字段的宽度。
- 服务端对同一 kind 缓存上一份 payload 并跳过完全相同的重发；新增字段若每次变化都会破坏这个去重，需确认反射频率可接受。

## 五、addon 命令约定

- 请求：客户端 `Dream_SendData("名字", 参数)`。
- 应答：服务端 `sDoAddon->SendPacketToClient(player, "名字", 载荷)`。
- 服务端分发两种风格并存：`IsPacket(RHMsg, "名字")`（多数）与模块内 `header == "名字"`（`BeastCardMgr`）。
- 参数字段分隔符历史上 `#` 与 `$` 混用，改协议前必须对照该命令两端实现，不要按“全局规范”推断。
- 新增或改名命令要同时改三处：Lua 发送、Lua 接收分支、服务端分发；漏一处就是静默失效的按钮。
- 该通道不再扩展；新功能走 opcode。`BeastCard*` 与 `SecretPlace*` 的差异说明历史实现风格不统一。

## 六、退役通道（保留但不维护）

| 名称 | 原因 |
|---|---|
| `UITQ` whisper | 服务端已改用 `0x524/0x525`，`NativeUITooltipHandler.cpp` 只留注释 |
| `CheckSecretPlaceGuid` / `GetKeySecretPlace` / `GoNowSecretPlace` | 服务端 `sSecretPlaceMgr` 已弃用（`AsCreature.cpp` 中相关调用被注释） |

这四项写在 `Test-AddonCommandSync.ps1` 的 `KnownUnhandled` 里；一旦某天服务端补回处理，脚本会提示把它们从名单移除。
