# 客户端装备 Tooltip 自定义属性渲染方案

## 1. 目标

目标是让客户端在鼠标指向装备、背包查看、装备栏查看、聊天物品链接、拍卖行或交易窗口查看物品时，直接在原生物品提示框内显示：

- 装备名称、品质、物品等级、绑定和部位；
- 基础属性，例如护甲、耐力、智力、精神；
- 自定义属性，例如强化值、鉴定属性、成长属性、伤害范围、评分；
- 镶嵌槽、已镶嵌宝石和镶嵌奖励；
- 随机效果、触发效果、套装效果或装备系列效果；
- 现有客户端已经显示的耐久、需求等级、装备售价等内容。

用户不需要另行安装插件。界面和绘制逻辑随客户端发布，服务端只负责保存、校验和同步装备的权威状态。

## 2. 截图中的 `item:` 是什么

截图中的字符串类似：

```text
item:37196:0:0:0:0:0:0:80:1:2153
```

其中 `37196` 是物品 Entry。后面的冒号字段用于携带附魔、宝石、随机属性、词缀种子和物品等级等链接参数。

当前客户端的 `ItemLinkInfo` 已经保存这些标准字段：

- `m_itemId`：物品 Entry；
- `m_enchants[12]`：附魔和宝石相关 ID；
- `m_propertySeed`：随机词缀种子；
- `m_randomPropertiesId`：随机属性或随机后缀 ID；
- `m_level`：链接中的物品等级。

解析入口是 `ItemLinkInfo::GetItemIdFromLink()`。它从 `item:` 开始读取字段，在读取 `m_level` 后返回。截图最后的 `2153` 不属于当前解析器已定义的字段，当前代码不会把它自动保存为自定义属性或装备 GUID。

因此，普通物品链接只能作为“物品识别和标准参数”的入口。强化等级、随机效果说明、鉴定属性和玩家装备实例数据不能默认依赖链接尾部，除非同时扩展链接格式、解析结构、生成代码和所有接收窗口。

## 3. 当前客户端已经具备的能力

### 3.1 原生 Tooltip 框体

客户端通过 `CGTooltip` 注册 `GameTooltip`，原生流程会调用 `SetItem()` 创建装备提示框。`CGTooltip` 已提供：

- `CreateItemLink()`；
- `GetItemHyperlinkString()`；
- 物品链接解析；
- 物品品质颜色；
- 附魔、宝石、随机属性和标准物品属性的显示。

`Tooltip_Scripts.cpp` 还会把 `CGTooltip` 暴露给 Lua，因此可以选择在原生 Tooltip 流程末尾追加客户端内置脚本绘制。

### 3.2 客户端静态物品数据

`ItemStats_C` 已包含客户端物品表中的以下数据：

- `m_displayId`、品质、物品等级、需求等级；
- 最多 10 组基础属性类型和值；
- 武器伤害和攻击速度；
- 随机属性、随机后缀和物品套装 ID；
- 最多 3 个镶嵌槽、槽内内容和镶嵌奖励；
- 耐久、绑定、部位及其他标准字段。

这些数据来自客户端物品缓存或物品查询结果，适合绘制静态属性和标准 Tooltip 内容。

### 3.3 物品实例字段

客户端 `CGItemData` 已接收服务端同步的物品实例字段，包括：

- 附魔数组；
- 属性种子和随机属性 ID；
- 耐久度和最大耐久度；
- 物品所有者、容器和 GUID；
- 动态标志和其他原生物品状态。

背包或装备栏中的真实物品可以从客户端对象取得这些字段。聊天链接、拍卖行条目和部分检查窗口只有链接参数，没有本地物品对象，因此需要额外的服务端数据或可验证的扩展链接。

## 4. 数据应该由谁负责

服务端负责最终结果，客户端负责展示结果。

服务端必须负责：

- 装备是否存在、是否属于当前玩家；
- 强化、鉴定、随机效果、镶嵌和套装资格；
- 计算最终数值，尤其是大整数和百分比；
- 防止客户端伪造装备属性；
- 装备变化后的版本号和完整状态；
- 登录、重连、切图和检查他人时的同步。

客户端负责：

- 解析物品链接和原生 Item 对象；
- 保存按物品 GUID 或链接签名索引的动态 Tooltip 数据；
- 把服务端字段转换为中文文本、颜色和图标；
- 将动态行插入原生 Tooltip 的固定位置；
- 在装备字段、物品字段或服务端扩展数据变化后刷新 Tooltip；
- 对缺失、过期、非法或不匹配的数据安全回退。

不要让客户端根据 ItemID 自行推导玩家的强化结果。相同 ItemID 的不同装备实例可能有不同强化、随机属性和镶嵌状态。

## 5. 推荐的数据模型

建议在客户端增加一个独立的动态装备数据缓存，不修改 `ItemStats_C` 的静态物品表语义。

```text
DynamicItemTooltip
  itemGuidLow       物品实例低 GUID，可选
  itemEntry         物品 Entry
  revision          服务端版本号
  itemLevel         最终显示物品等级
  armor             最终护甲
  stats[]           属性类型和值
  sockets[]         槽位颜色、已镶嵌内容、槽位状态
  randomEffects[]   随机效果文本或效果 ID 与参数
  setInfo           系列 ID、当前件数、激活门槛、效果
  extraLines[]      经过服务端校验的附加 Tooltip 行
  signature         服务端签名或校验值，可选
```

其中 `extraLines[]` 只适合已经确定为显示文本的内容。若客户端需要本地化、颜色、图标或条件显示，优先传结构化字段和 ID，不要把任意未校验的富文本直接拼进客户端。

建议使用两种索引：

1. 有真实物品对象时使用 `itemGuidLow + itemEntry`；
2. 只有链接时使用 `itemEntry + propertySeed + randomPropertiesId + enchant/socket 参数 + 服务端签名`。

仅用 ItemID 做索引会把同一模板的不同实例错误合并。

## 6. 推荐运行流程

```text
鼠标指向物品
    -> 原生 Tooltip 解析 Item 对象或 item 链接
    -> 读取客户端静态 ItemStats_C 和标准链接字段
    -> 根据 GUID 或链接签名查 DynamicItemTooltip
    -> 若缓存版本匹配，直接追加自定义行
    -> 若没有数据，向服务端请求一次 Tooltip 数据
    -> 服务端校验请求并返回结构化装备状态
    -> 客户端校验版本、Entry、GUID 和签名
    -> 更新缓存并重新绘制当前 Tooltip
```

装备变化时走增量刷新：

```text
服务端装备/强化/镶嵌变化
    -> 保存数据库并递增 revision
    -> 推送 ITEM_TOOLTIP_DATA_UPDATE
    -> 客户端更新缓存
    -> 若当前 Tooltip 正在显示该物品，调用重新构建
```

登录、重连、切图时发送当前玩家装备的完整快照。聊天链接、拍卖行和交易窗口按需查询单个物品，避免把所有角色装备数据广播给所有玩家。

## 7. 协议建议

### 7.1 采用客户端内置协议

当前 NativeUI 已有握手、快照和 Lua 桥接，可以作为客户端内置 UI 的基础。但当前通用快照字段主要面向单位资源和界面数据；装备 Tooltip 的结构化数组、GUID、槽位和版本号不适合长期塞进普通 `key=value` 字符串。

建议增加独立的客户端内置消息，例如：

```text
CMSG_ITEM_TOOLTIP_QUERY
  version
  requestId
  itemGuidLow   可选
  itemEntry
  propertySeed
  randomPropertiesId
  context       背包/装备/聊天/拍卖/交易/检查

SMSG_ITEM_TOOLTIP_DATA
  version
  requestId
  result
  itemGuidLow
  itemEntry
  revision
  itemLevel
  statCount + stats[]
  socketCount + sockets[]
  randomEffectCount + effects[]
  setInfo
  signature
```

字段使用明确宽度、固定字节序和长度上限。客户端不能直接发送 C++ 结构体内存布局。

### 7.2 与 NativeUI 的关系

NativeUI 适合承载 Tooltip 管理器、装备图鉴、套装面板和低频状态通知。原生 Tooltip 动态行建议由 C++ 提供结构化数据，再由内置 Lua 或 C++ 的 `CGTooltip` 完成绘制。

如果复用现有 NativeUI 快照，至少要增加新的 kind 或 payload 类型，并明确：

- 最大物品数量、最大文本长度和最大属性数量；
- GUID 与请求 ID 的对应关系；
- 重复响应、超时和断线重连；
- 旧客户端收到未知 kind 时的回退；
- 不允许把任意服务器文本当作脚本执行。

### 7.3 现有插件消息不能直接作为最终方案

服务端当前 `AddonActive` 目录已有类似 `AutoBigItemStatData`、`AutoBigItemWeaponData` 和按 GUID 发送随机装备数据的逻辑。这些代码说明服务端已经有动态属性来源，但它们目前走插件消息和字符串协议。

迁移到客户端内置渲染时，可以复用这些数据计算函数和数据库语义，重新编码为原生世界包。客户端不再等待插件注册，也不再依赖插件频道或插件字符串拆包。

## 8. Tooltip 绘制位置

建议把渲染拆成三层：

### 第一层：原生标准内容

继续使用现有 `CGTooltip::SetItem()` 和标准 ItemStats 流程，负责名称、品质、护甲、基础属性、槽位、耐久、需求等级和售价。

### 第二层：动态实例属性

在标准属性完成后追加：

- 强化等级；
- 鉴定结果；
- 动态伤害范围；
- 动态属性值；
- 随机效果；
- 套装系列进度。

动态行应该拥有自己的行标记或内部段落 ID，刷新时只重建动态段，避免每一帧重新查询数据库或重建完整 Tooltip。

### 第三层：交互提示

在 Tooltip 底部追加客户端内置的操作提示，例如查看套装详情或打开镶嵌界面。点击操作仍然发请求给服务端，服务端再次校验物品 GUID、槽位、权限和资源消耗。

## 9. 镶嵌和随机效果的处理

原生 `ItemStats_C` 已有三组槽位颜色、槽内内容和槽位奖励字段；真实物品对象还会同步附魔数组。标准宝石显示可以继续走原生字段。

自定义镶嵌需要区分：

- 槽位本身由 ItemID 模板决定；
- 当前镶嵌由物品实例决定；
- 镶嵌奖励由服务端最终计算；
- 未识别的宝石或效果 ID 必须显示为安全的未知状态，不得崩溃。

随机效果不能只依赖客户端随机种子重新生成。客户端可以用标准 `randomPropertiesId` 显示原生随机词缀；自定义随机效果应由服务端返回最终效果 ID、参数或已本地化的文本，并带 revision。

## 10. 需要调整的客户端代码范围

实施时预计涉及以下范围：

1. `WoW/Source/UIUtil/Tooltip.h/.cpp`：扩展动态装备数据结构、缓存索引和 Tooltip 动态段刷新入口。
2. `WoW/Source/UIUtil/Tooltip_Scripts.cpp`：为内置 Lua 暴露读取当前 Tooltip 物品、动态属性和刷新接口。
3. `WoW/Source/Object/ObjectClient/Item_C.*`：在物品实例字段更新时清理或刷新对应动态缓存。
4. `WoW/Source/Client.cpp`：注册消息处理器、请求入口和内置数据桥接。
5. `WoW/Source/Net/Types.h` 或项目实际协议定义文件：增加请求和响应消息，并核对 12340 线字段。
6. `WoW/Source/Ui/GameUI.cpp`：在 UI 初始化和销毁阶段注册/清理内置 Tooltip 模块。
7. `Interface/NativeUI/`：放置内置 Lua 绘制逻辑、颜色、文本和 SavedVariables；此目录随客户端发布，不要求玩家单独安装插件。

如果决定把所有绘制逻辑放在 C++，可以减少 Lua 桥接，但会增加文本本地化、布局和迭代成本。推荐先由 C++ 负责协议、缓存和校验，由内置 Lua 负责行布局和颜色。

## 11. 需要调整的服务端代码范围

服务端实施时预计涉及以下范围：

1. 从物品实例、强化模块、幻境模块、随机装备模块和镶嵌系统汇总最终显示数据。
2. 增加 Tooltip 查询请求处理器和响应编码。
3. 装备、强化、镶嵌、随机效果变化后递增 revision 并推送更新。
4. 登录、重连、切图时发送当前玩家装备的完整快照。
5. 对聊天链接、拍卖行、交易和检查目标增加按需查询权限判断。
6. 为动态数据增加长度、数量、GUID、Entry 和签名校验。

现有 `GetNItemLink()` 生成的普通链接可以继续保留。只有在确认需要把“无 GUID 的聊天链接”也完整展示为动态装备时，才考虑扩展 `item:` 链接；否则优先使用服务端原生查询消息，避免破坏 12340 客户端的链接兼容性。

## 12. 不建议的做法

- 只把所有自定义文字拼到 `item:` 链接尾部，然后期待原生客户端自动显示；当前解析器不会读取这些尾字段。
- 只按 ItemID 缓存属性；不同物品实例会互相覆盖。
- 让客户端根据随机种子自行计算服务端强化结果；会造成显示和实际属性不一致，也可被篡改。
- 每次鼠标移动都向服务端请求；应使用 GUID/签名缓存和 revision。
- 把装备 Tooltip 数据全部放进每帧更新；Tooltip 是事件驱动的，应在数据变化或框体重建时刷新。
- 继续依赖插件频道作为内置客户端的唯一数据入口；没有插件加载时这条链路不存在。

## 13. 分阶段实施顺序

### 阶段 A：只读验证

- 用现有客户端显示一件普通物品、一件带随机属性的物品、一件带宝石的物品；
- 记录 `ItemLinkInfo` 实际解析出的字段；
- 确认服务端动态属性在物品实例、数据库和现有插件消息中的来源；
- 确认截图最后的 `2153` 是否为物品 GUID、版本号或其他自定义字段。

### 阶段 B：先支持真实物品对象

- 只处理背包和装备栏中有真实 GUID 的物品；
- 增加原生消息、客户端缓存和 Tooltip 动态段；
- 验证强化、镶嵌、随机效果变化后实时刷新。

### 阶段 C：扩展无 GUID 链接

- 支持聊天、拍卖、交易和检查窗口；
- 采用链接参数加服务端签名或 requestId 查询；
- 明确物品链接转发、缓存过期和权限规则。

### 阶段 D：完善内置界面

- 将装备系列面板、套装详情和镶嵌操作界面放入客户端 `Interface/NativeUI`；
- 由客户端安装包统一发布；
- 清理对外置插件目录和插件频道的依赖。

## 14. 验收标准

至少覆盖以下场景：

- 背包装备 Tooltip 显示静态属性和动态属性；
- 装备栏 Tooltip 显示同一件物品的最新状态；
- 强化、洗练、镶嵌、拆除、随机效果变化后立即刷新；
- 同一个 ItemID 的两件物品显示各自的实例属性；
- 其他玩家查看装备时只获得允许查看的数据；
- 聊天链接、拍卖行、交易和检查窗口不会显示错误实例数据；
- 登录、重连、切图后缓存恢复正确；
- 服务端返回非法 ID、过长文本、过多属性、错误签名时客户端安全回退；
- 客户端没有对应静态 ItemRec 或资源时仍能显示基础链接，不崩溃；
- 不安装插件时，Tooltip 和装备系列界面仍能工作。

## 15. 当前决策点

开始改代码前需要确定三件事：

1. `2153` 的真实语义，是物品 GUID、版本、装备等级还是其他自定义参数；
2. 动态属性是否必须支持聊天/拍卖行/交易等无 GUID 场景；
3. Tooltip 动态行采用内置 Lua 排版，还是全部由 C++ 绘制。

建议先选“真实物品 GUID + 原生消息 + 内置 Lua Tooltip 行”作为第一阶段，完成后再扩展无 GUID 链接。这样能先验证数据闭环、刷新时机和服务端权威性，再决定是否需要修改 `item:` 链接格式。
